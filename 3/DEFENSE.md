# Памятка к защите

## Что сказать о программе

Я вычисляю определитель рекурсивным разложением по первой строке. Верхние уровни заранее превращаю в независимые задачи: у каждой своя матрица-минор и накопленный множитель со знаком. Фиксированный пул потоков забирает задачи из общего массива. Мьютекс защищает только индекс следующей задачи. Каждый работник накапливает отдельную сумму. Основной поток тоже считает, потом дожидается работников и складывает результаты. Число потоков задаётся `-t` и включает основной.

## Структуры в начале determinant.c

- `Matrix`: размер `n` и одномерный массив `values`. Индекс элемента: `row*n+col`. Максимальный размер 14. Фиксированный буфер упрощает работу с памятью, но занимает место даже для небольших миноров.
- `Task`: оставшаяся матрица `matrix` и `factor` — произведение коэффициентов разложения и знаков с верхних уровней.
- `Pool`: массив `tasks`, его заполненность `count`, выделенная ёмкость `capacity`, индекс следующей задачи `next`, пауза для демонстрации и общий мьютекс.
- `Worker`: указатель на общий пул и личная сумма `result`.

## Основные функции: порядок чтения

1. `make_minor`, строка 99: пропускает первую строку и выбранный столбец, записывает остальные элементы в новый буфер. `index++` последовательно заполняет его.
2. `determinant`, строка 109: база `n==1`; цикл по первой строке; построение минора; рекурсивный вызов; чередование плюса и минуса по чётности столбца.
3. `prepare_tasks`, строка 123: та же верхняя часть разложения, но при достижении нужной глубины сохраняет задачу вместо дальнейшего вычисления. `factor` накапливает коэффициенты и знаки. `realloc` расширяет массив, `memcpy` копирует используемые элементы матрицы. Всё это происходит до запуска потоков.
4. `take_task`, строка 152: захват общего мьютекса; проверка `next<count`; выдача `next++`; освобождение мьютекса. Возвращает `true`, если задача есть.
5. `worker`, строка 162: превращает `void *` обратно в указатель на `Worker`; при необходимости ждёт для показа через ОС; получает задачи циклом; считает их и накапливает личный результат.
6. `main`, строка 193: ключи, вход, подготовка задач, выделение данных работников, запуск `p-1` потоков, работа основного, `join`, сложение результатов и очистка.

Остальные функции обслуживают ввод и ошибки: `parse_number`, `read_matrix`, `check_thread`, `fail`, `now`, `usage`.

## Главный участок main

```c
for (size_t i = 1; i < count; ++i)
    pthread_create(&threads[i], NULL, worker, &workers[i]);

worker(&workers[0]);

for (size_t i = 1; i <= created; ++i)
    pthread_join(threads[i], NULL);
```

Это сокращённая схема; в настоящем коде ошибки проверяются. Цикл создания начинается с 1: нулевую долю исполняет основной поток. Данные работников выделены заранее и не освобождаются до `join`. При ошибке создания основной и уже созданные работники завершают вычисления, после чего программа сообщает об ошибке и возвращает ненулевой код.

## Короткие ответы

**Почему нет гонки при выдаче?** Проверка наличия задачи и увеличение `next` находятся внутри одной критической секции под одним общим мьютексом.

**Почему суммы без мьютекса?** Каждый поток пишет только в `result` своего `Worker`. Основной читает их после завершения потоков через `join`.

**Почему не держать мьютекс при вычислении?** Тогда одновременно считал бы только один поток, остальные ждали бы замок.

**Чем отличается pthread_create от fork?** Создаёт поток внутри существующего процесса с общей памятью. У потока свои регистры, стек и TID; PID процесса общий.

**Зачем pthread_join?** Дождаться завершения конкретного работника, после чего безопасно читать его результат и освобождать используемые им данные. Join не запускает поток.

**Почему не создавать поток на каждый вызов рекурсии?** Число вызовов растёт факториально; создание и обслуживание потоков дорого и нарушит лимит. Здесь новые задачи не создают новые потоки.

**Где лежат миноры?** Матрицы задач скопированы в массив задач в куче; временный `Matrix minor` в рекурсии находится в стеке соответствующего потока. Задачи после подготовки только читаются.

**Зачем calloc?** Выделить память и обнулить её; личные суммы работников начинают с нуля. `malloc/realloc` сами значения не обнуляют.

**Что значит void *?** Указатель общего типа. В worker восстанавливаем тип `Worker *`, чтобы обратиться к полям аргумента.

**Почему число потоков иногда меньше -t?** `-t` задаёт верхнюю границу. Работников больше, чем задач, не создаём.

**Почему long double?** Поддерживает вещественные элементы и обычно даёт больший диапазон/точность, чем double; конкретные свойства зависят от платформы. Вычисление не является произвольной точной арифметикой.

**Как обрабатываются ошибки pthread?** Они возвращают номер ошибки напрямую; в `check_thread` передаём его в `strerror`. Проверять только errno было бы неправильно.

## Что искать в реальном strace

Файл `report/evidence/strace-t4.txt`:

- `clone3(...)= -1 ENOSYS`: эта версия ядра/среда не обслужила новый интерфейс; библиотека переключилась на `clone`.
- Три успешных `clone(...)=TID`: три дополнительных потока, плюс основной даёт четыре.
- `CLONE_VM`: общая память; `CLONE_FILES`: общая таблица дескрипторов; `CLONE_THREAD`: одна группа потоков процесса.
- `clock_nanosleep`: наша пауза `-w 2` для удобного показа, не часть полезных вычислений.
- `futex(...FUTEX_WAIT_BITSET...)`: в этом фрагменте основной ждёт завершения работника. Не каждый futex обязательно относится к нашему мьютексу.
- `exit(0)` у работников; `exit_group(0)` при завершении процесса.
- `<unfinished ...>` / `<... resumed>`: вызов начался, strace показал события других потоков, затем вернулся к его завершению.

`pthread_create`, `pthread_join`, `pthread_mutex_lock` — библиотечные функции. Strace показывает системные вызовы под ними, поэтому искать буквальные названия pthread-функций неправильно. Успешный захват свободного мьютекса часто вообще не вызывает ядро.

В `ps-t4.txt`: один PID, четыре различных TID, `NLWP=4`. Указанные четыре строки подтверждают существование четырёх потоков, а не их одновременное выполнение на четырёх ядрах: снимок снят во время паузы.
